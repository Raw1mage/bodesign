# Architecture

## Product Boundary

This repository will host `bodesign` as a host-agnostic MCP server plus web server. Any MCP-capable client (IDE, agent, or HTTP caller) provides files or design instructions through MCP over a Unix socket (local) or TCP port (external). The system boundary starts with source ingestion and normalization: datasheet/schematic/BOM-like evidence extraction, Gerber/drill/IPC upload, public reference-board evidence, and normalized component/design knowledge. Those normalized records feed `BoardDesign IR` generation/reconstruction, layout planning, `/bodesign/` circuit/PCB rendering, Gerber generation, deterministic validation, approval, and export. bodesign is independently operable; no host shell or gateway owns the product boundary. Factory test/debug guidance is deferred to a later phase.

- `services/api`: FastAPI/Python backend for project APIs, Postgres-backed design jobs, storage access, web APIs, MCP tool handlers, AI orchestration, validation, approval, Gerber generation, and export.

- `packages/design-ir`: Product-owned PCB source of truth, evidence model, schema validation, and versioning. `ComponentInstance` carries optional comparator fields (`value`, `optional`, `flexible_pin_groups`). The `compare/` submodule (G7) is a deterministic reference comparator: two-stage component matching (required first; optional reference parts free), pin-neighborhood signatures, pure-Python Hungarian assignment, symmetric-passive pin normalization (`__sym__`), FlexiblePin groups, and weighted score `S = 0.4·S_comp(Dice) + 0.2·S_attr + 0.4·S_conn` (weights centralized in `ScoringConfig`; CMP_CONFIG_INVALID on bad weights). Mismatch details are CrossCheckDiffItem dicts (dimension component/pin/component_value + first_divergence) and wrap into a ValidationEvidence envelope (`tool="crosscheck"`) via `to_validation_evidence()`. Invalid input IR fails fast (CMP_IR_INVALID, no partial comparison); same input yields byte-identical output, no LLM involvement.
- `packages/component-kb`: Datasheet ingestion, part-number resolution, pinout/package normalization, interface grouping, and layout-rule knowledge. The `spice_card.py` module (knowledge/datasheet-spice-models) is a deterministic datasheet-grounded SPICE model pipeline over vault L4: `ingest_spice_extraction` validates an extraction batch row-by-row (registry leaf / evidence sha256+page / numeric value; per-row SPX_FIELD_UNKNOWN/SPX_EVIDENCE_MISSING/SPX_VALUE_INVALID rejection; `not_found` reported but never written; all writes trust=unverified), `generate_model_card` renders byte-identical `.model`/`.subckt` cards from the L4 `spice_model.{diode,ldo,passive}` namespace (typ-selection: typ→single→SPX_PARAMS_AMBIGUOUS, no averaging; provenance comment header, no timestamps; SPX_PARAMS_MISSING/SPX_CATEGORY_UNSUPPORTED fail-fast), and `materialize_model_cards` runs an ngspice DC-op smoke (pass/fail/skipped-no-simulator; fail cards excluded) then writes cards + a `manifest.json` (`source=vault-grounded`) into `<project>/spice/models/` — the `spice` skill's model-resolution cascade tier-1 cache, so vault-grounded models win without any skill change. LLM participates only in upstream extraction; this module is fully deterministic.
- `packages/doc-core`: OpenMV schematic/datasheet evidence extraction and design-intent normalization.
- `packages/reverse-core`: Rockbox evidence extraction and IR reconstruction. Current implementation parses Allegro `cds2f` placement/BOM-like exports into component instances and IPC-D-356A records into net/pad/via summaries; Gerber/drill geometry extraction, net inference beyond IPC evidence, and component clustering remain next steps.
- `packages/source-core`: `BoardDesign IR` patch validation and source export helpers.
- `packages/gerber-core`: Python-first Gerber adapter around `pygerber`, geometry normalization, manufacturing checks, output comparison, and validation.
- `packages/shared`: Shared schemas and API types.
- `tests`: Fixture-based backend, frontend, and workflow tests.

## Data Flow

1. User provides chip models, target functions, OpenMV reference documents, Rockbox component placement/BOM-like files, Gerber/artwork, drill, IPC netlist, routing/report files, and optional annotations.
2. FastAPI stores raw files and creates a Postgres project/job record.
3. Source-ingestion pipeline classifies each input as component evidence, design-intent evidence, manufacturing evidence, or reference-board evidence.
4. Component knowledge pipeline extracts part numbers, resolves/ingests datasheets, and normalizes pinout/package/power/interface/layout knowledge.
5. Document and artifact pipelines extract evidence into a shared evidence model.
6. OpenMV flow generates initial `BoardDesign IR`; Rockbox flow reconstructs `BoardDesign IR` from component placement, IPC net/pad/via summaries, Gerber/drill manifests, and confidence evidence.
7. `/bodesign/` retrieves `BoardDesign IR`, layer summaries, parsed component positions, IPC net summaries, confidence overlays, component knowledge, and generated output data for Canvas 2D rendering.
8. Validation checks verify IR schema, component knowledge coverage, connectivity evidence, DRC-like constraints, and generated Gerber outputs.
9. AI invokes EDA MCP tools to ingest knowledge, propose layout plans, reconstruct Rockbox, generate datasheet-derived designs, or create IR operations; deterministic validators gate every operation.
10. User reviews generated layout/Gerber candidates in `/bodesign/` or an IDE/host proposal UI and approves selected outputs.

## Safety and State Rules

- AI suggestions are advisory until converted into typed `BoardDesign IR` operations.
- No layout or Gerber output is considered final without user approval.
- AI does not directly route copper or emit final fabrication files; deterministic IR validation, bridge export, and Gerber validation are required.
- Patch validation is deterministic and must fail fast on unsupported operations.
- `BoardDesign IR` is the source of truth for generated/reconstructed layouts.
- Component knowledge records are evidence-linked and confidence-scored; unknown datasheets must produce explicit gaps instead of silent assumptions.
- Raw uploads, normalized evidence, `BoardDesign IR`, generated Gerbers, findings, proposals, approvals, and exports remain separate states.

## Verification Baseline

- Component knowledge extraction, document extraction, artifact parsing, IR generation, and reconstruction behavior should be fixture-driven.
- Verification-judgment knowledge (plan `plans/quality_verify-knowledge-hardening/`): the first deterministic **ERC classification checker** turns raw KiCad ERC output into engineering verdicts rather than a bare violation count. `eda-bridge/kicad_emit.py` `classify_erc_report(report_text, declared_nc=None)` is a pure-python, zero-LLM, fail-fast parser that buckets each violation into `real_short` (two named nets touching — CRITICAL), `pad_net_bug` (empty/single second net — generator bug), `unconnected` (should-connect pin left open — defect), `intentional_nc` (a `pin_not_connected` whose `REF.PIN` is in the spec-declared `nc` list — demoted to INFO, T1), or `other` (unparseable lines preserved verbatim, never dropped — no silent fallback). `blocking_count` excludes `intentional_nc`, so a power-only board's deliberately-open USB-C D+/D-/SBU pins no longer inflate the error count. `ErcClassification` is mounted on `KiCadValidationResult.erc_classification` (existing `erc_violations`/`erc_errors` semantics unchanged, backward-compatible). This is the first landing of the 8-domain PCB-verify knowledge extracted from public engineering sources into bodesign's ragbase (`workflow.pcb-verify-8-domains`, `concept.no-connect-classification`, `concept.pin-net-ssot-verification`, `control.dfm.jlcpcb-ipc-thresholds`, `control.placement.post-place-quality-checks`); the `pin_not_connected` block format is calibrated against a real kicad-cli 9.0.9 `.erc.rpt`, while the short/net-conflict code list is a documented assumption (no real short fixture available) to be calibrated when one is obtained.
- Verify-checker skillification (plan `plans/quality_verify-checker-skillification/`): the second landing generalises the one-off ERC classifier into a **systematic control→checker injection architecture** so the 57 distilled `control.*` objects can be enforced rather than sit as static knowledge. Core lives in `packages/workflow-core/bodesign_workflow_core/checkers/`. Every checker follows the `classify_erc_report` DNA — pure-python, zero-LLM, fail-fast (`CheckerError` CHK_* family in `errors.py`, explicit `missing_fields[]`, never a default substitution), byte-identical output — and emits the shared `ValidationEvidence` envelope carrying `control_id` + `source_anchor` so every verdict is datasheet-grounded (DD-2). **DD-1 executability tiers** classify each control objectively: T-A machine-checkable (verified + numeric threshold + IR-readable → hard gate), T-B semi/IR-gap (verified rule but the gated quantity is absent from design IR → registered as a stub exposing the parser gap, never faked), T-C advisory-only (qualitative or partial/todo → design-review prompt, no hard gate — no-fabrication). **DD-3 knowledge↔code runtime coupling**: thresholds are NEVER hard-coded — `threshold.py resolve_threshold_block(db, control_id)` reads a structured `threshold_block` (metric/value/unit/source_anchor) from the owning ragbase control's `metadata_json` at run time, so a re-distilled threshold propagates with zero code change; it fails fast (`CHK_THRESHOLD_UNBOUND`) rather than parse `body_md` prose to invent a number, and rejects a block with no `source_anchor` (`CHK_SOURCE_ANCHOR_MISSING`). **DD-4 registry** (`registry.py CheckerBinding`/`build_pilot_registry`) is the single inspectable skillification panel (control_id · tier · trust_layer · stage · checker_fn · ir_fields · status), joins landed T-A checkers to `ORACLE_TOOLS` (a typo'd envelope_tool fails fast), and enforces the no-fabrication guard (a partial/todo control cannot register as T-A). - **Source-code contract lint — `control.quality.no-silent-degradation`** (BR_20260729, KB `ragbase/control/no-silent-degradation/`): the first checker whose subject is **bodesign's own Python**, not a design IR. It exists because one C04 delivery round produced five defects of one shape — `net2pcb` dropping 8 active ICs while returning `ok:true unmapped:0` (§B), `placement_preflight` silently falling back from a non-existent courtyard API to a silkscreen-inclusive bbox and reporting `utilization 1.27` (§C), `plane_layers=["In1.Cu:GND"]` being dropped by a bare-name lookup so a 4-layer board got no power planes at all (§D), extent measured two different ways in two functions so a fitting board was rejected as too small (§E), and preplace optimising around footprint origins while pcbnew drew courtyards elsewhere (§F) — **all of which passed the entire test suite**, because the tests asserted happy-path correctness and never asserted that a partial failure is visible in the return value. The invariant: *a partially-completed operation must not be readable as complete*; the review question that operationalises it: **if the caller reads only `ok` or a single count, can they reach a wrong conclusion?** Five variants are distinguished because their fixes differ: V1 element dropped, V2 measurement degraded unmarked, V3 status flag not reflecting an internal downgrade (all **false-green**, fixed by making the degradation visible); V4 the same quantity implemented in several places and V4-b the same quantity carrying different reference-frame assumptions (both **false-red** — the gate is correct and its input is wrong, fixed by converging implementations / making the frame explicit, NOT by adding a `basis` field). `checkers/no_silent_degradation.py` is a pure-AST lint whose tiers were assigned by **measured signal-to-noise**, scanning `routing.py` before and after the fixes: L2 (`except` that only passes/logs in a value-returning function) 2→0, L6 (caller-supplied key fails `.get()` with no else — the §D shape, which has no `continue` at all and so is invisible to L1) 1→0, L8 (one measurement API implemented in >1 function, keyed by receiver so `pad.` vs `fp.` are not conflated) 1→0 → all **T-A**; L1 (loop `continue` not recording the skipped element) 19→19, hitting regex-mismatch and keep-ring filters that legitimately mean "this one was never ours to process" → honestly demoted to **T-C advisory, off by default**, because 19 noise findings would bury 3 real ones and nobody would run the lint. L5 (implausible-value tripwire) is deliberately **not** a lint — it is a runtime domain check, whose reference implementation is `placement_preflight`'s `implausible_measurement` (utilization > 1.0 is geometrically impossible, so the verdict is reported UNUSABLE rather than a confident `passed:false`). It is deliberately **not registered in `registry.py`**: every row there is a control→design-IR checker (`ir_fields` are IR paths, `stage` is a C00–C04 pipeline stage, evidence flows through `ORACLE_TOOLS`), and a source-code lint has none of those — registering it would require inventing fake `ir_fields`, which is the very fabrication this control forbids. Run via `python3 -m ...no_silent_degradation packages services/mcp`; current repo baseline 11 true positives (L2×8, L6×3), recorded in the KB object rather than silently carried. Tests: `tests/test_no_silent_degradation.py`, 15 green — including two anchored to real history (the T-A rules MUST fire on `1269a20~1` and MUST be clean on HEAD), so the tier decision itself stays falsifiable.

The map is a hand-written list, i.e. exactly the V4-c shape, so `tests/test_check_c03_gate_reachability_and_netlist.py` **re-derives the audit from source** and fails if a third eager offender appears. **(§1) BOM↔netlist consistency had no gate at all**: `check_c03`'s signature had no netlist parameter, so it was *structurally incapable* of answering the question its own GUIDE row advertised ("drawability"); R3 only checks that a BOM row *claims* a symbol source. Client↔MCP storage share: the product should follow a docxmcp-like split where the client owns durable files and exposes a scoped project folder manifest/read/write capability to the MCP. The MCP can analyze, split PDFs into source chunks, render online views, suggest edits, and write back through that scoped share; it should not silently migrate user content into server-owned durable storage. Required open design points include manifest schema, permission scope, cache invalidation, conflict handling, and whether writes are direct MCP writes or client-applied patch operations.

Project folder UX: users should not see an exploded machine intermediate tree at the root. The human-facing project root should stay close to KiCad/EDA concepts: `docs/` or `inputs/` for datasheets, application notes, reference designs, and incoming manufacturing packages; `eda/` for KiCad-native `.kicad_pro`, `.kicad_sch`, `.kicad_pcb`, project settings, and reviewable schematic/board sources; `libraries/` for project-local symbols, footprints, 3D models, and vendor libraries; `outputs/` for reviewed PDFs, Gerbers, drill files, BOM, pick-and-place/position files, STEP/3D exports, and release packages; `reports/` for reconstruction/validation summaries. Machine-only data — source chunks, OCR/table extraction, normalized IR, parse caches, embeddings, render artifacts, provenance indexes, workflow state, and temporary bridge outputs — belongs in a hidden/system workspace such as `.bodesign/`. The MCP manifest maps standard EDA folder locations to semantic roles and the MCP web UI exposes internals as evidence views without making the underlying folder structure noisy.
